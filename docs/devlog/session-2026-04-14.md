# Session 2026-04-14: Fork Child Investigation & Container PID Simplification

## Problem Statement

Two symptoms when running `apt-get update`:

1. **ubuntu-rootfs**: `FAKELINUX_ROOT=ubuntu-rootfs ./target/debug/fakelinux --container ubuntu-rootfs/bin/bash -c "apt-get update"` sometimes hangs, sometimes can't verify data
2. **tttt-root**: `FAKELINUX_ROOT=tttt-root ./target/debug/fakelinux --container ubuntu-rootfs/bin/bash -c "apt-get update"` claims keys are missing

## tttt-root Key Issue (Simple, Separate)

The tttt-root is a **Debian sid** rootfs, not Ubuntu. It uses `sqv` (Sequoia PGP) instead of `gpgv` for signature verification. The error:
```
Missing key 4CB50190207B4758A3F73A796ED0E7B82643E131
Missing key B8E5F13176D2A7A75220028078DBA3BC47EF2265
```
These are Debian archive signing keys. The keys exist in `tttt-root/etc/apt/trusted.gpg.d/` as `.asc` files, but `sqv` may need them in a different format or location. This is a separate issue from the fork bug.

## ubuntu-rootfs Hang: Fork Child Runs Parent Code

### Symptom

The gpgv method's internal fork child runs the METHOD's processing code instead of exec'ing the real gpgv binary. This causes apt-get to hang indefinitely.

### Which child breaks?

**Always the gpgv method's fork**, never apt-get's direct forks. The process chain:
1. apt-get (PID 1 in container) forks children for http and gpgv methods -- **these forks WORK**
2. gpgv method (exec'd via fork+exec from apt-get) forks to exec real gpgv -- **this fork BREAKS**

The broken child is reproducible (happens every run) and always affects the same child in the process tree.

## Completed: Container PID Simplification

**Implemented and committed.** Replaced shared-memory-backed full PID table with a much simpler scheme:
- Only PID 1 is virtual (the init process started with `--container`)
- All other processes use their real macOS PID as their virtual PID
- Removed ~200 lines of shared memory / PID table infrastructure
- Benefits: host tools (ps, lsof) can inspect processes; eliminates PID mismatch bugs

Key API changes in `pidns.rs`:
- `attach_container(init_pid: i32)` — takes just the init's real PID
- `set_child_env()` — no arguments needed
- `current_vpid()` → 1 for init, real PID otherwise
- Removed: `register_fork`, `update_entry`, `unregister_vpid`, `list_active_pids`, shared memory

## Deep Investigation: The Fork Bug

### Diagnostic Infrastructure Added

1. **`FORK_TRAP_COUNT`** (trap.rs): logs first 50 UDF traps (SVC + MRS/MSR + x18) in fork children with pc, register values, sp, lr
2. **`FORK_SVC_COUNT`** (existing): logs first 10 SVCs in fork children
3. **Canary verification**: checks `[canary_addr]` vs saved canary at each SVC trap
4. **`FORK_RETURN_PROBE`**: patches `__libc_fork`+0xC1D28 (`mov w0, w19`) to UDF, logs x19/lr at the exact return point
5. **`FORK_LR_WATCH`**: monitors `[__libc_fork_sp + 0xE8]` (saved LR on stack) at each trap to detect corruption

### Theories Tested and Results

#### Theory 1: TLS/Stack overlap corrupts canary (from diary 2026-04-13)
**DISPROVED.** Stack is at ~0x7FF0_0000_0000 (512GB), TLS is at ~0x1030-0x1050 range (~4GB). Distance is ~480GB. Canary verification shows **canary=Y for ALL SVCs** in all children. The STP in _Fork writes to [TPIDR-0x668] which is in TLS, far from stack.

#### Theory 2: __libc_fork returns non-zero due to canary check failure
**DISPROVED.** The FORK_RETURN_PROBE at __libc_fork+0xC1D28 shows **x19=0x0** for ALL children (both working and broken). This means __libc_fork's `mov w0, w19` correctly sets w0=0.

#### Theory 3: Something between __libc_fork's return and ExecFork's cmp changes x0
**PARTIALLY CORRECT but the root cause is deeper.** ExecFork's child path starts with `signal(SIGPIPE, SIG_DFL)` → rt_sigaction. Working children show SVC#1=rt_sigaction(13). Broken child shows SVC#1=fstatat (parent's `FileFd::Size()` code). So ExecFork's `cmp w0, #0` sees non-zero.

#### Theory 4: __libc_fork returns to wrong address (LR corruption)
**CONFIRMED AS ROOT CAUSE.**

### ROOT CAUSE FOUND: Saved LR Corruption on Stack

The FORK_RETURN_PROBE reveals:
- **Working children**: `lr=0x10xxx77dc` (correct return address in ExecFork, libapt-pkg)
- **Broken child**: `lr=0x50000b728` (HEAP ADDRESS! Points to brk region, not code)

The saved LR is at `[__libc_fork_sp + 0xE8]`. In the broken child, this stack slot contains a heap address instead of the correct return address.

**Critical finding**: The corruption exists BEFORE our macOS fork() is called:
```
lr_before_fork = 0x50000b728  (already corrupted!)
lr_after_fork  = 0x50000b728  (same)
```

This means the PARENT process (gpgv method) has a corrupted stack before it even calls fork(). The LR was wrong when `__libc_fork` saved it at entry (`stp x29, x30, [sp, #224]`).

### Additional Finding: Temporary LR Corruption in All Children

Even **working children** experience LR corruption during `__libc_fork`'s child path:
```
TRAP#9:  LR_CORRUPTED expected=0x10xxx77dc got=0x10xxxcd4  (libc code address)
TRAP#16: LR_CORRUPTED expected=0x10xxx77dc got=0x7ff07fXXXX (stack address)
```
But by the time of the FORK_RETURN_PROBE (c1d28), the LR is RESTORED to the correct value. The broken child's LR was never correct to begin with, so there's nothing to restore.

### How __libc_fork Works (Ubuntu 24.04 glibc aarch64)

#### _Fork (offset 0xBD4C0):
```asm
bd4c0: stp x29, x30, [sp, #-0x10]!
bd4c4: mrs x5, tpidr_el0            ; PATCHED to UDF
bd4c8: mov x0, #0x11                ; SIGCHLD
bd4d4: movk x0, #0x120, lsl #16    ; CLONE_CHILD_SETTID|CLONE_CHILD_CLEARTID
bd4d0: sub x4, x5, #0x670           ; child_tidptr = TPIDR-0x670
bd4e8: svc #0                        ; clone → INTERCEPTED by fakelinux
bd4ec: cmn x0, #1, lsl #12
bd4f4: mov w2, w0                    ; save fork return
bd4f8: cbnz w0, bd514               ; parent skips child work
bd4fc: sub x6, x5, #0x740           ; child: x6 = TPIDR-0x740
bd500: sub x0, x5, #0x660           ; robust list head = TPIDR-0x660
bd50c: stp x0, x0, [x6, #0xd8]     ; write robust list to TLS
bd510: svc #0                        ; set_robust_list (SVC#0 in trace)
bd514: mov w0, w2                    ; restore fork return
bd518: ldp x29, x30, [sp], #0x10
bd51c: ret
```

#### __libc_fork (offset 0xC1B50):
```asm
c1b50: sub sp, sp, #0x140           ; allocate frame
c1b60: stp x29, x30, [sp, #224]     ; save fp(sp+0xE0) and LR(sp+0xE8) ← LR SAVED HERE
c1b68: stp x19, x20, [sp, #240]     ; save callee-saved
c1b6c: ldrb w19, [x1, #1320]        ; single-threaded flag
c1b84: str x1, [sp, #216]           ; save canary at sp+0xD8
c1b98: cbz w19, c1d88               ; slow path if multi-threaded
c1b9c: bl _Fork                      ; fast path: call _Fork
c1ba0: mov w19, w0                   ; save fork return in w19
c1ba4: cbnz w0, c1ce0               ; parent path if non-zero
; child path: c1ba8-c1cdc
c1bdc: mrs x26, tpidr_el0           ; PATCHED to UDF (TRAP#1)
; ... thread list cleanup (may call malloc → TRAP#2-18) ...
c1ccc: mov w19, #0                   ; fork return = 0
c1cd0: bl d5790                      ; atfork child handler
; return path:
c1d08: adrp x0, ...                  ; canary check setup
c1d10: ldr x2, [sp, #216]           ; saved canary
c1d14: ldr x1, [x0]                 ; TLS canary
c1d20: b.ne c1f0c                    ; → __stack_chk_fail if mismatch
c1d24: ldp x29, x30, [sp, #224]     ; RESTORE fp and LR ← LR LOADED HERE
c1d28: mov w0, w19                   ; set return value (0 for child)
c1d3c: ret                           ; return to caller via LR
```

#### ExecFork(set<int>) (libapt-pkg offset 0xB77C4):
```asm
b77c4: paciasp
b77c8: stp x29, x30, [sp, #-64]!
b77d8: bl fork@plt                   ; call fork() → __libc_fork
b77dc: cmp w0, #0                    ; check return
b77e0: b.lt error
b77e4: mov w19, w0                   ; save fork return
b77e8: b.eq b7800                    ; child path: signal setup + exec
; parent path: return pid
b7800: ; child path starts here
b780c: bl signal@plt                 ; signal(SIGPIPE, SIG_DFL) → rt_sigaction SVC
; ... more signal setup, then opendir("/proc/self/fd"), close fds, return 0 ...
```

### What We Know For Sure

1. **Our fork trampoline correctly sets x0=0** (ASM_X0=0x0 confirmed)
2. **Stack canary is never corrupted** (canary=Y at all check points)
3. **__libc_fork's child path correctly sets w19=0** (FORK_RETURN_PROBE confirms x19=0x0)
4. **The saved LR at [sp+0xE8] is corrupted to a HEAP address** (0x50000bxxx)
5. **The corruption exists BEFORE fork is called** (lr_before_fork already wrong)
6. **Working children also experience temporary LR corruption** during __libc_fork's child path, but it's restored before return
7. **The broken child is always the gpgv method's internal fork** (second-level fork)
8. **The gpgv method process has a corrupted stack** before calling __libc_fork

### What Needs Investigation Next

The LR at [sp+0xE8] in __libc_fork's frame is corrupted BEFORE fork. This means something in the **gpgv method process** writes to this stack location before or during the __libc_fork call.

Possible causes:
1. **Data patched as code**: Our patcher replaces SVC/MRS/x18 bit patterns with UDF. If data bytes matching these patterns were patched, reading the "data" later would yield UDF values instead of the original. If a global pointer is stored in patched data, it could contain garbage.
2. **Stack buffer overflow**: One of the gpgv method's shared libraries has a buffer overflow that writes past its frame into __libc_fork's saved registers.
3. **Stale pointer from thread list**: glibc's thread list (populated during library loading) has a pointer that writes to the stack region.
4. **PAC (Pointer Authentication)**: The guest binaries use `paciasp`/`autiasp`. On Apple Silicon, these are real PAC instructions. If the signing key or context differs between signing and verification, the PAC might corrupt the pointer's upper bits. However, the corrupted value (0x50000bxxx) doesn't look like a PAC-mangled address.

### Suggested Fix Approach

Since `lr_before_fork` captures the ALREADY-CORRUPTED LR, the fix at fork time is too late. Options:
1. **Fix the root cause** by finding what corrupts the stack in the gpgv method
2. **Work around it** by saving the correct LR EARLIER (e.g., when ExecFork calls fork@plt, intercept and save LR at that point)
3. **Detect and repair** by reading the correct return address from ExecFork's stack frame (which should still have the correct LR saved by `paciasp` / `stp x29, x30`)
