# Session 2026-04-14: Fork Child Investigation & Container PID Simplification

## Problem Statement

Two symptoms when running `apt-get update`:

1. **ubuntu-rootfs**: `FAKELINUX_ROOT=ubuntu-rootfs ./target/debug/fakelinux --container ubuntu-rootfs/bin/bash -c "apt-get update"` sometimes hangs, sometimes can't verify data
2. **tttt-root**: `FAKELINUX_ROOT=tttt-root ./target/debug/fakelinux --container ubuntu-rootfs/bin/bash -c "apt-get update"` claims keys are missing

## tttt-root Key Issue (Simple)

The tttt-root is a **Debian sid** rootfs, not Ubuntu. It uses `sqv` (Sequoia PGP) instead of `gpgv` for signature verification. The error:
```
Missing key 4CB50190207B4758A3F73A796ED0E7B82643E131
Missing key B8E5F13176D2A7A75220028078DBA3BC47EF2265
```
These are Debian archive signing keys. The keys exist in `tttt-root/etc/apt/trusted.gpg.d/` as `.asc` files, but `sqv` may need them in a different format or location. This is a separate issue from the fork bug.

## ubuntu-rootfs Hang: Fork Child Runs Parent Code

### Symptom

The gpgv method's internal fork child runs the METHOD's processing code instead of exec'ing the real gpgv binary. This causes apt-get to hang.

### Which child breaks?

**Always the gpgv method's fork**, never apt-get's direct forks. The process chain:
1. apt-get (PID 1 in container) forks children for http and gpgv methods -- **these forks WORK**
2. gpgv method (exec'd via fork+exec from apt-get) forks to exec real gpgv -- **this fork BREAKS**

### Deep Investigation with FORK_TRAP Diagnostics

Added `FORK_TRAP_COUNT` counter (50 entries) that logs ALL UDF traps (SVC, MRS/MSR tpidr_el0, x18 instructions) in fork children. This gives a complete picture of every intercepted instruction.

#### Working child trace (apt-get's direct fork, e.g., http method):
```
TRAP#0:  SVC set_robust_list  pc=libc+0xBD510  (inside _Fork child path)
TRAP#1:  MRS x26, tpidr_el0   pc=libc+0xC1BDC  (__libc_fork child path)
TRAP#2:  SVC rt_sigaction      pc=libc+0x3CC88  (atfork handler called from c1cd0)
TRAP#3+: SVC rt_sigaction (more signal setup), then openat/execve etc.
```

#### Broken child trace (gpgv method's fork):
```
TRAP#0:  SVC set_robust_list  pc=libc+0xBD510  (inside _Fork child path) -- SAME as working
TRAP#1:  MRS x26, tpidr_el0   pc=libc+0xC1BDC  (__libc_fork child path) -- SAME as working
TRAP#2:  MRS x22, tpidr_el0   pc=libc+0x96604  (__libc_malloc!)        -- DIFFERENT!
TRAP#3-18: More MRS in malloc (0x96604, 0x94FC8) and related functions
TRAP#19: MRS x6, tpidr_el0    pc=libc+0x57E34  (_IO_vfprintf)
TRAP#20: SVC fstatat           pc=libc+0xDD2C4  (method's parent code)
TRAP#21: SVC geteuid
TRAP#22: SVC faccessat2
... (method processing code, NO execve)
```

### Key Finding: malloc in __libc_fork's child path

The critical difference: the broken child enters `__libc_malloc` (offset 0x96604 in libc) during `__libc_fork`'s child path, while working children skip malloc entirely.

Both children correctly enter the child path (TRAP#0 and #1 match). But the broken child's glibc thread-list cleanup code triggers malloc, which working children don't do.

### Root cause analysis: glibc's fork child path + malloc lock ordering

In `__libc_fork`'s child path (fast path, offset c1ba8):
```asm
c1bdc: mrs x26, tpidr_el0       ; get TPIDR
c1be0: sub x23, x26, #0x740     ; thread descriptor
...
c1bd0: ldr x3, [x20, #4488]     ; load pending-thread flag
c1c00: cbnz x3, c1e3c           ; if non-NULL, branch to thread list manipulation
; thread list loop at c1c18-c1c48:
c1c18: sub x28, x25, #0xc0
c1c3c: tbnz w1, #0, c1d40       ; branch for thread with pending data
; at c1d40: cleanup involving memset, possible malloc
...
c1ccc: mov w19, #0              ; set fork return = 0
c1cd0: bl d5790                  ; call atfork child handler (releases locks)
```

The sequence is:
1. glibc acquires ALL internal locks (including malloc arena locks) BEFORE fork (at c1b90)
2. Our fork trampoline does the actual macOS fork()
3. In child, glibc's child path runs thread-list cleanup (c1c00-c1d84)
4. Thread-list cleanup calls **malloc** while arena locks are still held
5. Then atfork child handler (c1cd0) releases locks

The gpgv method process has a non-trivial thread list (loaded many shared libraries with TLS), causing step 3 to actually iterate. The cleanup code at c1d40 calls memset and potentially other functions that trigger malloc. Since malloc arena locks are held from step 1 (and NOT yet released -- that happens at step 5), the malloc call may:
- Deadlock (if mutex is non-recursive)
- Allocate from a fallback arena (potentially corrupting state)
- Return memory that aliases other structures

```
bd4c0: stp x29, x30, [sp, #-0x10]!

bd4f4: mov w2, w0                    ; save fork return

bd500: sub x0, x5, #0x660           ; robust list head = TPIDR-0x660

bd50c: stp x0, x0, [x6, #0xd8]     ; write robust list to TLS
bd510: svc #0                        ; set_robust_list (SVC#0 in trace)
bd514: mov w0, w2                    ; restore fork return

```

#### __libc_fork (offset 0xC1B50):
- Entry: sub sp, #0x140; save callee-saved regs; save stack canary at [sp+0xd8]
- Fast path (single-threaded): calls _Fork at c1b9c
- After _Fork child return (w0=0): c1ba0: mov w19, w0; c1ba4: cbnz w0, parent
- Child path: thread list cleanup, atfork handlers, canary check
- Return: c1d28: mov w0, w19; ret (w19 was set to 0 at c1ccc)
- Canary check: c1d20: b.ne __stack_chk_fail (compares [sp+0xd8] with TLS canary)

### Memory layout (no TLS/stack overlap)

Stack is at ~0x7FF0_0000_0000 (512GB), TLS is at ~0x1030-0x1050_0000_0000 (~4GB). Distance is ~480GB. The previous theory about TLS/stack overlap causing canary corruption does NOT apply with the current memory layout. The STP at _Fork+0x4C writes to [TPIDR-0x668], which is in the TLS region, far from the stack.

### Diagnostic infrastructure added

1. `FORK_TRAP_COUNT` (trap.rs): logs first 50 UDF traps (SVC + MRS/MSR + x18) in fork children
2. `FORK_SVC_COUNT` (existing): logs first 10 SVCs in fork children
3. Format: `FORK_TRAP#N TYPE pc=... details x0=... x19=... lr=...`

### What to investigate next

1. **Is malloc the cause?** The malloc calls in the child path (before atfork handler releases locks) may corrupt state. Need to verify if malloc deadlocks, returns NULL, or corrupts other data.

2. **Does __libc_fork actually return 0?** Need to determine if the canary check passes and w0=0 when __libc_fork returns to the caller. The fstatat at TRAP#20 could be:
   - Caller's PARENT code (fork returned non-zero) → bug
   - Caller's CHILD code that does fstatat before exec → needs investigation

3. **Container mode PID interaction**: After macOS fork, `MY_VPID` (static AtomicI32) still has the PARENT's vpid. If the child calls getpid() before exec, it gets the parent's vpid. While most code uses fork()'s return value, some programs compare getpid() with a cached value.

4. **CLONE_CHILD_SETTID writes real PID, not vpid**: In our fork trampoline:
   ```rust
   let child_tid = unsafe { libc::getpid() };
   unsafe { (child_tid_ptr as *mut i32).write(child_tid); }
   ```
   This writes the macOS real PID, not the virtual PID. If glibc code later compares pthread->tid with getpid() (which returns vpid in container mode), the mismatch could cause issues.

### Canary Check PASSES — TLS/Stack Overlap Theory DISPROVED

Added canary verification to FORK_TRAP logging. Result: **canary=Y for ALL SVCs in the broken child**. The stack canary is NEVER corrupted. This definitively rules out the diary's TLS/stack overlap theory (which was based on an older memory layout).

### SP Analysis

SP values from FORK_TRAP show the broken child:
- TRAP#0 (set_robust_list): sp=0x7ff07fef10 (inside _Fork)
- TRAP#1 (MRS __libc_fork child): sp=0x7ff07fef20 (__libc_fork's frame)
- TRAP#2-18 (malloc): sp varies 0x7ff07fea00-0x7ff07ff000 (nested calls)
- TRAP#19 (vfprintf): sp=0x7ff07fe490 (deep in call stack)
- TRAP#20 (fstatat): sp=0x7ff07feb60 (returned to caller)

### ExecFork Disassembly Reveals the Path

APT's `ExecFork(set<int>)` at libapt-pkg+0xb77c4:
```asm
b77d8: bl fork@plt          ; call fork()
b77dc: cmp w0, #0           ; check return
b77e0: b.lt error            ; error path
b77e4: mov w19, w0           ; save return
b77e8: b.eq child_path       ; if 0, child path (signal setup, exec)
; parent path: return fork value
```

Child path starts at b7800 with `signal(SIGPIPE, SIG_DFL)` → `rt_sigaction(13, ...)`.

Working children show SVC#1 = rt_sigaction(13) — correctly entering child path.
Broken child shows SVC#1 = fstatat — parent's `FileFd::Size()` code.

**Conclusion**: `ExecFork`'s `cmp w0, #0` sees non-zero, causing parent path.
But our fork trampoline sets x0=0 and canary is intact, so `__libc_fork` should return 0.

### Current Theory: Something Between __libc_fork Return and ExecFork's cmp Changes x0

Possible causes:
1. Signal delivery between `__libc_fork`'s `ret` and `ExecFork`'s `cmp` that corrupts x0
2. A glibc atfork handler that modifies the return value
3. The malloc calls in the thread-list cleanup corrupt __libc_fork's w19 or w0

### Next step: Runtime patching diagnostic

Patch the instruction at __libc_fork+0xc1d28 (`mov w0, w19`) to UDF in the fork child. When it fires, log w19 (the fork return value that will become w0). This catches the exact value right before __libc_fork returns.

## Container Mode PID Simplification (Proposed)

Current approach: fully virtual PIDs (vpid 1 for init, auto-incrementing for others) mapped to real PIDs via shared memory table.

Proposed simplification: only PID 1 is virtual (mapped to the init process's real PID). All other processes use their real macOS PID as their virtual PID. Benefits:
- Eliminates most PID translation complexity
- Host tools (ps, lsof) can directly inspect fakelinux processes
- Removes potential PID mismatch bugs (CLONE_CHILD_SETTID, pthread->tid)
- Simplifies debugging enormously
- Only wait4() for PID 1's children needs special handling
