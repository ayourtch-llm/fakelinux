## ⚠️ Methodology prerequisite (READ FIRST — applies to every item below)

**Most of these failures are timing-dependent.** A naive isolated re-run of a failing
class may pass, or fail intermittently. Therefore, for **every** item:

1. **First establish a reliable repro** — a command/loop that reproduces the failure
   with high probability (ideally ≥80% over N runs) *before* touching any code.
   Use a loop harness (run the class K times, tally failures) — never trust a single
   green/red run.
2. **Only then** write the fix.
3. **Verify against the same repro loop** — the fix must take the failure rate to ~0
   over at least as many iterations as the repro needed to show it. A single passing
   run is **not** acceptance.
4. Watch for **load sensitivity**: some bugs only appear under full-suite CPU pressure
   (multiple VPP instances + SIGILL trap tax). When an isolated loop won't reproduce,
   reproduce under artificial load (run the class concurrently with a CPU hog, or
   inside a partial suite slice) before concluding "not reproducible."
5. Record the established repro (and its observed hit-rate) in this doc next to the item.

Order of attack (agreed): **IPsec first** (largest, most reproducible) → **other
isolated clusters** → **harness crash (§D)** → **full-suite rerun** to find whatever was
hidden past the truncation point.

## A. IPsec ESP / tunnel corruption — THE big cluster (~110 of 127) 🎯

### A.1 Symptoms (exact messages)
All point to **packet payload/header memory corruption**, concentrated on the
chained-buffer (large-packet) path. Distinct error tails observed:

```
AssertionError: <n> != <n> : Invalid packet checksum on layer #1: ICMP: ... (28x)
AssertionError: <n> != <n> : Invalid packet checksum on layer #0: IP: ...   (6x)
AssertionError: <n> != <n> : Invalid packet checksum on layer #1/#2: ICMPv6 Echo Req/Reply (14x)
vpp_pg_interface.CaptureMismatchError: captured 66 packets, expected 67 ...  (11x; also 126/127, 99/100, 65/67, 49/50)
AssertionError: 0 is not true            # pkt.haslayer(GRE) → header corrupted (5x)
IndexError: Layer [IP] / Layer [Raw] not found   # structure corrupted
ValueError: invalid length of packed IP address string
```

**Smoking gun for memory corruption** — the inner address decodes to garbage:
```
AssertionError: '::1' != 'fd01:2::2'
AssertionError: '127.0.0.1' != '172.16.2.2'
AssertionError: '1102:ecc3:c4c0:1f3e:edb6:c19:682c:142b' != 'fd01:2::2'
AssertionError: '9bba:70c:6d25:6ab9:8a38:9a0b:64d0:da8f' != 'fd01:2::2'
AssertionError: 'ab80:....:f778:a344' != 'fd01:1::2'
```
Random-looking 16-byte values where a known IPv6 address should be = raw memory bytes
leaking into the packet. This is **not** a crypto bug — see handoff §5.3/§5.4 (GCM tag
is valid ⟹ ciphertext correct ⟹ corruption is in the decrypt output write / scatter-
gather at the buffer1→buffer2 boundary).

### A.4.1 REPRO ESTABLISHED (2026-06-28) ✅
`scripts/vpp-shell.sh '/tmp/esp_repro_loop.sh 12'` → **12/12 FAIL** (rc=2; 10 FAIL,
2 ERROR). 100% reliable class-level repro. Dominant failure mode is
`Invalid packet checksum on layer #1: ICMP/ICMPv6` (the `esp_scan.py` heuristic only
catches IPv4-ICMP in `*-out-*.pcap`, so it under-reports — caught corruption in only
1/12 runs, but the test fails every run). One captured corruption sample:
```
-out-0003.pg1_out.pcap pkt5 icmp_chk=0x0c14 off=[1060..1075]
  vals=0xb4,0xdc,0x87,0x34,0xc2,0x5e,0x65,0xdf,0xf1,0x10,0x73,0x1f,0x8d,0x87,0xee
```
**Signature: exactly 16 contiguous bytes of random data** = one cipher block / one
128-bit vector register. The corruption is a single 16-byte write going wrong.

Mechanism note: fakelinux only emulates/rewrites instructions that **reference x18**
(the macOS-reserved register); native AES/PMULL crypto runs on hardware. So if the bug
is in emulation it must be an x18-referencing 128-bit store. The trampoline `emit()`
(`x18_trampoline.rs:265`) DOES write back a modified base register (steps 6-7), so
post-index writeback to x18 is not lost — that hypothesis is ruled out. Next: empirical
`FAKELINUX_TRAP_STATS=1` on the failing run to see what is actually emulated in VPP's
crypto path.

### A.4.2 ★ ROOT CAUSE FOUND (2026-06-28) ★
**An async signal landing inside an x18-trampoline's SP-raised window corrupts the
guest's saved x16/x17 (the trampoline scratch registers), because the signal frame is
placed below SP with no red zone and overwrites the trampoline's `[sp,#-32]` save area.**

Chain of evidence (all via standalone repro `roots/ubuntu/tmp/gcm_repro.c` — AES-GCM
decrypt loop + 200µs SIGALRM, NO VPP needed, ~60s/run):
- Repro produces the identical signature: 1 corrupt 16-byte block / ~200k iters, tag
  valid, random content. With a heavier handler / no loop-syscall it also SIGSEGVs.
- **x18 emulation NOT the per-packet path** (VPP `x18_fallback=7`, `tramp_ok=5394` —
  startup-level). Crypto runs natively.
- macOS NEON snapshot is accurate (live CPU NEON == `mctx.ns` for v1–v31).
- Sigframe memory is intact between save and restore (frame CRC clean).
- **Scalar AES (`OPENSSL_armcap=0`, no NEON) ALSO corrupts** ⟹ general register-state
  corruption, not NEON-specific.
- Crash dumps show **x16/x17 garbage** (`x16=0x80001000, x17=0x0`) → wild store.
- x16/x17 are exactly the x18-trampoline scratch regs (`x18_trampoline.rs::emit`).

The trampoline (`emit`, ~line 302):
```
0: stp s1,s2,[sp,#-32]!   ; save scratch (x16,x17) at [sp]..[sp+8]
3: add sp,sp,#32          ; raise sp back to original so the wrapped instr sees correct sp
4: <orig instr, x18→s2>   ; sp == original, saved scratch now lives at [sp-32] (BELOW sp)
5: sub sp,sp,#32
8: ldp s1,s2,[sp],#32     ; restore scratch from [sp-32]
```
During step 4, live data sits at `[sp-32]`, below sp. AArch64 has **no red zone**, so an
async signal here → `build_sigframe_and_redirect` places the frame at `sp - 1424`,
clobbering `[sp-32]`. The guest resumes mid-trampoline, `ldp` reads the clobbered bytes →
x16/x17 wrong → wrong crypto block (or wild-store crash). Rare = the ~1-instruction
window. Verified: `FAKELINUX_NO_X18_TRAMP=1` (no trampolines) → no corruption.

### A.4.3 FIX
Give the synthesized signal frame a **red-zone gap below the guest sp** so it can never
overwrite trampoline scratch saved at `[sp-32]`. In
`signal.rs::build_sigframe_and_redirect`, place the frame at
`(guest_sp - REDZONE - RT_SIGFRAME_SIZE) & !0xF` with `REDZONE >= 32` (use 128/256 for
margin). One-line change; covers all callers (forwarder, trap SIGILL, deliver_pending).
**Verify against the gcm repro (0 corrupt over ≥500k iters) THEN the full
`esp_repro_loop.sh` (0/50) THEN the IPsec test files.**
Remove the temporary diagnostics afterward (SIGTRACE ring, frame CRC, SIGTERM dump,
per-pid trapstats file, gcm clobber modes).

### A.4.4 ⚠️ CORRECTION: the trampoline fix is REAL but is NOT VPP's bug
After landing the red-zone fix, **VPP's IPsec test STILL fails with the identical
16-byte corruption.** A collision detector (`sig_in_island`/`sig_in_window` counters,
gated by `FAKELINUX_SIGTRACE`, dumped via trap-stats) proved why:
- **Standalone repro:** `sig_in_island=8469, sig_in_window=38` (signals DO land in
  trampolines) → red-zone fix takes it to **bad=0** over 500k iters. Real bug, fixed.
- **VPP ESP test:** `sig_in_island=0, sig_in_window=0` — **no signal ever interrupts
  VPP inside a trampoline.** So VPP's corruption is a DIFFERENT root cause with the same
  16-byte signature.

What's now RULED OUT for VPP's IPsec corruption:
- x18 instruction emulation (VPP `x18_fallback=7`, per-packet crypto is native).
- The trampoline-scratch / async-signal collision (`sig_in_island=0`).
- Plain-code async-signal register save/restore (proven correct: NEON snapshot matches
  live; sigframe memory CRC clean).

**Lesson (fold into methodology §0):** a self-constructed repro must be confirmed to
reproduce *the same* bug as the target. The aggressive-SIGALRM gcm repro found a real
fakelinux bug but NOT VPP's — verify the repro tracks the target before trusting it.

The red-zone fix (A.4.3) is correct and should be KEPT/committed (fixes a genuine
signal-vs-trampoline corruption), but it does not move the IPsec cluster.

### A.4.8 ✅ NEON-across-signal RULED OUT 2026-06-29 (Claude) — the trail above is a wrong turn
The A.4.7 fix target ("fakelinux must preserve full 128-bit NEON across the trap") rested on
codex's claim that **macOS ignores NEON writes to the signal mcontext on return**. That claim
is FALSE — it came from a buggy probe. Decisive native experiments (all in
`roots/ubuntu/tmp/`, source kept):
- `neon_mctxwrite_probe.c` — SIGILL (SA_SIGINFO|SA_ONSTACK) handler writes
  `uc_mcontext->__ns.__v[0]` and returns → **HONORED** (this is exactly do_rt_sigreturn's
  path: trampoline `brk #0xf000` → SIGILL → trap_handler → `mctx.ns.v[]` write → return).
- `neon_mechprobe.c` — same write across **SIGILL, raise(SIGUSR1), setitimer(SIGALRM)** →
  **HONORED in all three**.
- `neon_coldfp_probe.c` — cold vs dirty FP before the trap → **HONORED both** (lazy-FP does
  not gate it).
- Why codex's `neon_mctx_probe` said "IGNORED": its disasm zeroes v0 in hardware
  (`mov.d v0[0],x9` / `mov.d v0[1],x9`, x9=0) **after** raise() returns and reads *that* back
  — it clobbered the handler's mcontext write before sampling, never reading the true
  post-signal v0.

Therefore the NEON signal round-trip is provably clean end-to-end: SAVE correct (codex's
FL_NEON_DBG: 0 mismatches), frame intact (CRC clean), RESTORE honored (these probes). The
residual ~1/285 (≈80/4000) "low-8-correct/high-8-garbage" corruption is **NOT** a lost-NEON-
across-signal bug. Codex's rt_sigreturn trampoline q0–q31 reload is therefore **redundant**
(committed as defensive WIP `bdbfebb`, clearly labeled "not the IPsec fix").

**Re-aim at MEMORY, not registers.** The high-8 garbage is most likely a stray store into the
decrypted output buffer, or a CTR/GHASH-state slip, async-triggered. Decisive next step is the
keystream-XOR discriminator (A.4.6) run on the **live** scapy repro (`scapy_gcm_sigalrm.py`),
not a C repro: for the corrupting block compute `(expected ^ ct)` and `(received ^ ct)`.
A valid-but-wrong-offset AES keystream block ⇒ CTR counter desync; `received ^ ct` unrelated
to `ct` ⇒ a stray write landed on the already-decrypted buffer (then `FAKELINUX_WATCH` that
16-byte region to catch the writer). Secondary audit: x18 emul store/writeback
(`emul_ldr_str_prepost`, `emul_ldp_stp` writeback) for a post-index or high-half slip.

### A.4.9 ★ DISCRIMINATOR RESULT 2026-06-29: STRAY MEMORY WRITE (not CTR-desync, not lost-reg)
Keystream-XOR discriminator run on the live scapy repro (`roots/ubuntu/tmp/scapy_gcm_ksdiag.py`,
companion Opus-4.8 agent). Verified model: `aes_key=key[:16]`, `salt=key[16:20]`, GCM
nonce96 = `salt||ESP_IV` (ESP_IV = `esp.data[:8]`), keystream block i = `AES-ECB(aes_key,
nonce96||int32(i+2))`. Confirmed in-guest: for clean blocks `AES-ECB(...) == ct_block ^ 0x58`.
(Caveat: `raw(dec)` recomputes inner IP/ICMP checksums, so the first ~2 blocks aren't ground
truth — analysis confined to the 0x58 payload region.)

Findings over ~10 corrupt samples (psize=1970, aggressive SIGALRM, 154 bad / 8000):
- The corruption is NOT really "16-aligned low-8-good/high-8-bad." In true ct/pt coordinates
  it is a contiguous run, **almost always 16 bytes, starting at offset ≡ 4 (mod 16)** (≡ 8 in
  scapy body coords) — it straddles two GCM blocks, which is why the per-block view looked like
  a half-block smear. Occasionally shorter (4/8/11 B) where foreign bytes coincide with 0x58.
- For every sample: `ks_used = received ^ ct` matches **no** keystream block at **any** byte
  shift (searched ±64 counters, all shifts); `received` matches no keystream slice and no ct
  slice; `received != ct_of_region` (not un-decrypted). So the implied keystream is **junk**,
  not a wrong counter ⇒ **CTR-desync RULED OUT** (the CTR engine used the right counters).
- **146/154 bad decrypts still PASS the GCM tag** (8 are InvalidTag). GHASH/tag is over the
  ciphertext *input*; a valid tag + corrupt plaintext ⇒ the stray write lands on the **output
  buffer AFTER decrypt**. The 8 tag-fails are the minority where the write hit the
  ciphertext-input/GHASH region instead.
- Garbage differs every occurrence (time-varying) ⇒ foreign source is a concurrently-running
  computation's data/stack ⇒ async race.

**Refined signature for the fix hunt:** a ~16-byte write of FOREIGN (time-varying) data landing
on the decrypt OUTPUT buffer at offset ≡ 4 (mod 16), correlated with an async signal during the
C decrypt — i.e. a misdirected 16-byte (NEON `stp`/`str q`) store, not a crypto-counter error.

**NEXT:** (1) close the one objection (Opus-4.7 companion): run `FAKELINUX_SIGTRACE=1` on the
live `scapy_gcm_sigalrm.py` and confirm the `do_rt_sigreturn` frame-CRC check (signal.rs:582–600,
"SIGFRAME-CORRUPT") never trips near a corrupting iteration — rules out frame-NEON-clobber
between BUILD and RESTORE masquerading as a memory bug. (2) Then `FAKELINUX_WATCH` the decrypt
output buffer region (offset ≡4 mod 16) to catch the exact guest PC doing the stray 16-byte
store; that instruction is the bug.

### A.4.10 ★★ ROOT CAUSE (strong, confirming) 2026-06-29: nested re-entrant signal_forwarder
Canonical repro committed: `tests/repro/gcm_signal_corruption.py` (no scapy/VPP; `cryptography`
EVP AES-GCM into a fixed buffer; verified ≥12 corrupt/8000 in-guest, 0 native). FAKELINUX_WATCH
(armed on an mmap-backed output buffer, watching the tail openssl never writes) caught the
writer: it is a **legit openssl `STUR x0,[…]`** in the GCM CTR XOR loop (`LDUR` ct → `EOR
x0=ct^ks` → `STUR x0`). So fakelinux is NOT writing a random address — the guest's own correct
store writes a **corrupted register value**: `x1` (the keystream) is wrong, foreign, time-varying
⇒ `ct ^ wrong_x1` = the junk plaintext (explains the keystream-XOR "no slice matches" verdict).

**Mechanism:** `signal_forwarder` is installed with an **empty `sa_mask`** (signal.rs ~1248), so
it is RE-ENTRANT, and unlike `trap_handler` it does not set `in_trap`. When a 2nd async signal
lands while `signal_forwarder` is mid-execution, the NESTED invocation reads the ucontext the
kernel captured *inside the outer forwarder's Rust execution* — so the "guest" `x1` it saves into
the inner sigframe is actually the outer forwarder's Rust register (garbage vs the guest). That
garbage propagates back and eventually lands in the openssl loop's `x1`. Fits all evidence: x1
wrong/foreign/time-varying, async-correlated (needs two signals close enough to nest),
single-threaded, same PC/LR otherwise, timing-gated (WATCH perturbation dropped the rate 3%→0.6%).

**FIX (apply after the nested-count counter confirms):** give `install_forwarder` a full
`sa_mask` via `sigfillset` so the kernel blocks signals during `signal_forwarder` (no nesting;
mirrors the existing SIGILL `trap_handler` sa_mask fix), OR an `in_forwarder` reentrancy guard
that defers the nested signal to `PENDING_SIGNALS`. Acceptance: `tests/repro/gcm_signal_corruption.py`
→ 0 bad over ≥8000 iters under aggressive SIGALRM (no WATCH).

**Side fix found (keep):** `host_anchor` host/guest PC-classification window was ±128 MB, so guest
openssl code within ~12 MB of host text was misclassified as host code (disarmed WATCH every run).
Tightened to ±4 MB in `src/trap.rs`. Real bug regardless of the above.

**⚠️ UPDATE — nested-forwarder hypothesis FALSIFIED (counter added).** `FORWARDER_NESTED = 0`
across 8000 iters with 247 corruptions ⇒ `signal_forwarder` does NOT nest: macOS auto-blocks the
in-flight signal during its own handler, and only SIGALRM is in play (self-nesting would need
`SA_NODEFER`). The `sigfillset` fix was therefore NOT applied (would be a no-op). The WATCH finding
still stands — the corrupting store is a legit openssl `STUR x0` writing a wrong `x1` (keystream).
Remaining viable mechanism under audit: the `trap_handler → do_rt_sigreturn → deliver_pending_to_guest`
path (signal deferred while `in_trap`, then re-delivered) writing/leaving a stale `mctx.ss.x[1]`.
KEEP the `host_anchor` ±4 MB fix and the `FORWARDER_NESTED/MAX_DEPTH` counters (cheap diagnostics).
(host_anchor ±4 MB fix + counters committed as `c45aafc`.)

### A.4.11 ★ x1-setter identified 2026-06-29: `LDR x1,[x27,#16]` — wrong keystream is from MEMORY
A 20-instruction back-disassembly before the corrupting openssl `STUR x0` (WATCH diagnostic in
`src/trap.rs`) shows the keystream register is loaded from memory: **`x1 = LDR [x27,#16]`** (a GPR
chain, no `fmov`-from-NEON), consistent with `OPENSSL_armcap=0` still corrupting (NEON-compute
already ruled out). So the wrong `x1` originates from a **memory** value, not a lost vector reg.
Now distinguishing (probe running, dumps `x27` and `[x27..x27+32]` at the store):
- (i) the keystream scratch at `[x27+16]` was **stomped by a stray write before the `LDR`** (memory
  corruption of openssl's keystream block — same stray-write family as A.4.9, just landing on the
  keystream buffer instead of the output buffer, then propagated via `ct ^ ks`); vs
- (ii) `x1` was corrupted **between the `LDR` and the `STUR`** (GPR loss across a signal round-trip,
  despite the frame CRC being clean); vs
- (iii) `x27` is itself a wrong pointer ⇒ `LDR` reads the wrong address.
Decisive read: if `[x27+16]` in memory at the store == the foreign `x1` ⇒ (i) memory stomp; if
`[x27+16]` is the CORRECT keystream but `x1` is foreign ⇒ (ii) register loss. Next: arm WATCH on the
keystream scratch `[x27+16]` to catch the stray writer's PC (if (i)), or audit GPR save/restore for
x1 between LDR/STUR (if (ii)).

**RESULT: (i) confirmed — a stray write into the live keystream buffer.** The x27/`[x27..+32]` dump
shows the AES-CTR counter input `[x27..+16]` is ALWAYS correct (`00 01 … 0B 00 00 00 03`) and `x27`
itself is correct, but the keystream output `[x27+16..+32]` is stomped — sometimes fully foreign,
and in one sample only **2 non-contiguous bytes (offsets 3 and 5)** differ from the otherwise-correct
keystream. A contiguous store can't hit only bytes 3 and 5, so it's either two sub-word writes or
(more likely) a wider foreign write that coincidentally matched the real keystream at the other
offsets. ⇒ openssl computes+writes the correct keystream, then **something byte-scribbles a few bytes
of it before the `LDR x1` reads it back** — a stray write into a live openssl heap buffer (NOT a
register loss; CRC-clean frame and honored NEON restores both still hold). NEXT probe (B): log
`mem[x27+16..+32]` at signal ENTRY (build_sigframe) and EXIT (do_rt_sigreturn) for the matching frame
(gated on the interrupted PC being in openssl crypto); if it changes to foreign values across one
round-trip, the stomper is in fakelinux's own signal code (binary-search build_sigframe/
do_rt_sigreturn). If memory is stable across signals yet still corrupts, the writer is off the signal
path → (A) FAKELINUX_WATCH_PC to arm WATCH on `[x27+16]` and catch the writer PC directly.

### A.4.5 NEXT for VPP's actual IPsec corruption (still open)
Leading suspects now (non-signal, non-x18): chained-buffer scatter-gather in
`esp_decrypt`, 16KB-page buffer-pool geometry, or a data-plane threading race. Concrete
steps:
1. Check whether the failing class runs VPP **worker threads** (`vpp_worker_count`) — if
   so, suspect a cross-thread race on the chained buffer (the 16-byte block = one torn
   SIMD copy). The "async off" only disables crypto-worker offload, not data-plane workers.
2. Reproduce inside a LIVE VPP (handoff §5.4 replay harness) and use `FAKELINUX_WATCH` on
   the actual corrupted buffer region to catch the wrong 16-byte store.
3. Build a VPP-faithful standalone repro: EVP AES-GCM over genuinely chained buffers
   (separate page-aligned 16KB allocations, ICV split across the boundary) WITHOUT
   aggressive signals — the no-signal gcm loop is clean, so the trigger is the
   buffer geometry, not timing.

### A.5 Investigation / fix approach (superseded by A.4.2/A.4.3 — kept for history)
1. Confirm & quantify the boundary corruption with the loop (A.4); capture the two
   chained-buffer guest addresses at a corrupting event.
2. Use **`FAKELINUX_WATCH`** software watchpoint (commit `7e933bb`) on the 2nd buffer's
   corrupted region to catch the exact store that writes the bad ~4 bytes; identify the
   guest instruction.
3. Cross-read VPP `src/vnet/ipsec/esp_decrypt.c` chained-buffer chunk building
   (`esp_decrypt_chain_*`, `op->chunks`) against fakelinux emulation of: buffer
   addresses, `memcpy`/`memmove` (check our SIMD/`emul_*` copy paths in `trap.rs`),
   and mmap/page alignment (16KB-page buffer-pool geometry — handoff §6 warns this may
   be the underlying cause, but unlike svm_fifo this is fixable in copy/layout emul).
4. Prime suspects (in order): (a) a NEON/SIMD store-pair or ld/st emulation that
   mishandles an address straddling a page or buffer boundary; (b) a memcpy-length /
   chunk-pointer arithmetic edge; (c) a trap landing mid-copy that loses a partial
   store. Note handoff §5.4 already RULED OUT the signal/sigreturn vector-save path and
   `emul_fmov`/`emul_simd_copy` by inspection — start from the watchpoint, not re-audit.

### A.6 Acceptance
